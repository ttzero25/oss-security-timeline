# ResearchOrchestrator

Input: an audited checkout pinned to an exact commit. Output: `orchestration.json`, isolated PoC evidence for supported candidates, and private GHSA/CVE drafts when every automated gate passes.

The orchestrator ranks code hypotheses with a recent-change boost and production-path preference, requires a default external reachability result, resolves a bounded runtime, and generates only allowlisted harmless marker-based reproductions. Unsupported candidates never consume the execution budget; supported candidates are selected with a language and vulnerability-class round robin. Automatic reproduction supports bounded synchronous or asynchronous Python command/code-execution paths, same-file SSRF functions, simple SQL query builders, direct file readers, direct `pickle.loads` wrappers and direct Flask template sinks, dependency-free JavaScript and Node 22+ TypeScript default exports, and single-file Go HTTP handlers. Python SSRF reproduction replaces supported HTTP clients with in-memory stubs, SQL reproduction passes a fake cursor to the real query-building function, path reproduction confines both files and the `..` input to a temporary scratch tree, and pickle reproduction uses a payload whose only effect is printing a unique marker. When Flask/Jinja is unavailable, the template path uses a narrowly compatible sink stub and records that it proves sink control rather than framework execution; the impact gate therefore remains partial. Unsupported candidates remain recorded with a reason instead of being reported as vulnerabilities.

The default verifier uses a temporary workspace, a reduced environment, timeout/output bounds, and additional OS resource limits on Linux. It is not a full file/network sandbox; `--container` remains available for stronger isolation. A successful contrast is not proof of novelty: the collected GitHub/OSV snapshot and the five-part evidence gate are recorded, and every generated draft states that broader human review is required. External submission is disabled and must be performed by a person.

Before Python execution, the build environment classifies imports as standard/installed, repository-local, safely stubbed by the selected generator, or missing. Missing imports stop the candidate because automatic dependency installation is disabled; the full preflight result is retained in orchestration evidence.
