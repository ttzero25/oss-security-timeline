OSS Security Timeline은 오픈소스 저장소의 업데이트와 공개 취약점 공지를 하나의 시간축으로 연결하고, 코드 가설을 제한된 PoC로 검증해 사람이 판단할 수 있는 제보 초안까지 만드는 로컬 보안 조사 플랫폼입니다.

대상 · 공개 GitHub OSS 운영 · 로컬 우선 제보 · 사람 최종 승인 상태 · 기능 검증 단계

제안 요약

분산된 업데이트·공지·코드 근거를 수동으로 맞추는 시간을 줄이고, “후보 발견 → 재현 → 중복 확인 → 근거 판정 → 제보 준비”를 동일한 기록 체계로 표준화합니다. 자동화의 목적은 취약점 확정이나 자동 신고가 아니라, 사람이 더 빠르고 일관되게 검토할 수 있는 증거 묶음을 만드는 것입니다.

핵심 산출물OSS별 보안 타임라인과 검증 근거
최종 통제외부 제출은 항상 사람의 결정
01 · BACKGROUND

해결하려는 문제

오픈소스 보안 조사는 데이터 부족보다 데이터가 서로 분리되어 있다는 데서 더 큰 비용이 발생합니다.

01

시간축이 분리되어 있음

릴리스, 커밋, CVE, GHSA, OSV의 게시·수정·최초 관측 시점이 각기 다른 화면과 형식에 흩어져 있어 사건의 순서를 재구성하기 어렵습니다.

02

탐지와 검증 사이가 끊김

정적 패턴은 후보를 만들 수 있지만 실제 외부 도달성, 기본 설정, 공격자 입력 통제와 정상·공격 대조가 없으면 제보 가능한 근거가 되지 못합니다.

03

조사 결과가 재사용되지 않음

기존 공지, 과거 보안 변경, fix 전후 코드와 PoC 관측이 한 기록에 남지 않으면 중복 조사와 판단 편차가 반복됩니다.

02 · PROPOSAL

제안 범위와 원칙

공개 정보 수집과 코드 연구를 연결하되, 자동화가 책임 있는 공개의 최종 판단을 대신하지 않도록 경계를 명시합니다.

제안 범위

  • 저장소·패키지별 업데이트와 CVE·GHSA·OSV 타임라인
  • 공지 별칭 통합, 취약점 유형, 영향·패치 버전 정리
  • 공지 참조 커밋의 fix 전후 코드 비교
  • 지원 언어의 source-to-sink 코드 가설과 도달성 판정
  • 자원 제한 정상/공격 PoC 대조와 재현 증거 보존
  • 기존 공지 중복 조사와 GHSA/CVE 비공개 초안 생성

의도적으로 제외

  • 후보 0건을 근거로 한 저장소 안전 판정
  • 미공개 제로데이 발생 건수의 단정적 예측
  • 모든 언어·프레임워크에 대한 완전 탐지 보장
  • 실제 서비스·네트워크·데이터베이스 대상 공격 실행
  • 근거 게이트를 건너뛴 취약점 확정
  • GHSA/CVE 외부 제출 또는 식별자 요청 자동화
03 · USERS

누가, 언제 사용하는가

반복 수집은 자동화하고 보안 판단은 연구자와 유지관리자에게 남기는 협업 모델을 전제로 합니다.

A

보안 연구자

관심 저장소를 등록하고 변경·공지·코드 후보를 한 흐름에서 검토하며 재현 가능한 증거를 축적합니다.

B

OSS 유지관리자

비공개 제보 초안에서 영향 경로, 정상 대조군, 관련 커밋과 중복 조사 내용을 빠르게 확인합니다.

C

보안 운영 팀

여러 저장소의 공지량·변경량·조사 상태를 비교하고 어떤 대상을 먼저 검토할지 결정합니다.

04 · CAPABILITIES

핵심 기능

현재 저장소에서 실행 가능한 범위를 기준으로 작성했습니다. “구현됨”은 정확성이나 완전 탐지를 보장한다는 의미가 아닙니다.

공개 데이터 추적

릴리스·커밋·저장소 및 패키지 보안 공지를 수집하고 CVE/GHSA 별칭과 관측 시각을 정규화합니다.

구현됨
Fix 전후 비교

영향·패치 버전과 공지 참조 커밋의 삭제·추가 코드를 연·월 및 파일별로 비교합니다.

구현됨
코드 가설 조사

Python, JavaScript/TypeScript, Go, C/C++ 및 일부 Actions 패턴에서 입력과 위험 동작의 연결 후보를 찾습니다.

지원 범위 한정
제한 PoC 검증

허용된 후보만 정상/공격 입력으로 대조하고 시간·CPU·출력·쓰기 범위를 제한합니다.

지원 후보 한정
관계망·요약

저장소, 패키지, 공지, CVE, CWE, fix 커밋과 코드 후보의 관계 및 OSS별 결과를 탐색합니다.

구현됨
제보 준비

다섯 근거 게이트를 통과한 결과만 GHSA 비공개 제보 초안과 CVE 요청 브리프로 정리합니다.

수동 제출
05 · ARCHITECTURE

두 레인, 하나의 근거 체계

타임라인 레인은 공개 사실을 수집하고, 연구 레인은 코드 가설을 단계별 게이트로 좁힙니다. 두 레인의 결과는 동일한 로컬 데이터와 리포트로 연결됩니다.

STAGE 01

수집·정규화

패키지, 릴리스, 커밋, CVE·GHSA·OSV를 공통 시간축으로 변환합니다.

STAGE 02

가설·도달성

지원 코드의 입력 경로와 위험 동작을 찾고 외부 진입점에서의 도달성을 확인합니다.

STAGE 03

격리 재현

제한된 PoC로 정상·공격 대조를 수행하고 실제 관측과 차단 이유를 기록합니다.

STAGE 04

판정·초안

중복과 다섯 근거를 검토해 사람이 제출할 비공개 제보 자료를 만듭니다.

07 · SAFETY

안전과 책임 있는 공개

보안 자동화의 품질은 무엇을 실행하는가뿐 아니라 무엇을 실행하지 않는가로도 평가해야 합니다.

후보 ≠ 취약점 ≠ 제로데이

정적 가설과 기계적 PoC 대조만으로 취약점을 확정하지 않습니다. 도달성, 기본 설정, 공격자 통제, 영향, 신규성과 사람의 코드 검토가 필요합니다.

HUMAN-IN-THE-LOOP
01

실행 격리

자원 제한 프로세스, 임시 scratch, 네트워크·DB 스텁, 해시 확인과 의존성 자동 설치 금지로 재현 범위를 좁힙니다.

02

증거 게이트

재현 성공만 보지 않고 기존 공지와 과거 변경을 함께 검토하며 근거가 부족하거나 오래된 스냅샷이면 초안을 차단합니다.

03

수동 공개

시스템은 GHSA/CVE 초안만 만들고 제출·식별자 요청·대외 커뮤니케이션은 담당자가 직접 수행합니다.

08 · ROADMAP

단계별 추진안

기간을 먼저 고정하기보다 각 단계의 종료 조건을 충족한 뒤 다음 범위로 확장하는 방식을 제안합니다.

PHASE 0 · CURRENT

기능 기반 확보

수집부터 제보 초안까지 단일 흐름과 로컬 웹을 검증합니다.

  • 타임라인·코드 조사 연결
  • 12개 역할 분리
  • 안전 게이트와 회귀 테스트
PHASE 1 · RELIABILITY

신뢰도와 관측성

실패·누락·상한을 사용자가 바로 판별하도록 만듭니다.

  • 수집 신선도·coverage 지표
  • rate limit·재개 안정성
  • 근거 완전성 검사 강화
PHASE 2 · COLLABORATION

팀 검토 체계

로컬 결과를 팀이 일관된 절차로 검토하도록 표준화합니다.

  • 검토 상태·승인 이력
  • 재현 번들 내보내기
  • 역할 기반 운영 가이드
PHASE 3 · COVERAGE

지원 범위 확장

벤치마크 근거가 확보된 언어와 취약점 유형부터 확장합니다.

  • 실제 공개 사례 평가 확대
  • 프레임워크별 의미 모델
  • 우선순위 모델 보정
09 · SUCCESS METRICS

성과를 어떻게 측정할 것인가

“취약점 수” 하나로 평가하면 과잉 탐지를 유도할 수 있으므로 운영 품질, 근거 품질, 연구 효율을 함께 봅니다.

영역측정 방법제안 종료 기준
수집 신뢰도성공·부분 완료·상한 도달·rate limit을 분리 집계모든 실행에 coverage와 중단 이유 기록
탐지 회귀버전 관리된 취약/정상 코퍼스와 고정 커밋 실제 사례 평가기존 지원 사례의 회귀 0건
재현 품질정상·공격 대조, 실행 범위, 대상 해시와 관측 결과 확인승격 후보의 증거 필드 누락 0건
오탐 관리도달성 실패, 중복, 미지원, 영향 부족 사유별 차단률차단 근거 없는 제보 초안 0건
검토 효율후보 생성부터 사람의 검토 완료까지 중앙값 측정파일럿 기준선 확보 후 단계별 개선
공개 안전성외부 자동 요청 및 자동 제출 여부 감사자동 제출 0건, 모든 제출에 사람 승인 기록
10 · RISKS

주요 위험과 대응

기술적 한계와 운영 리스크를 사전에 문서화하고 결과 화면에 그대로 노출합니다.

R1

API 제한과 과거 이력 누락

인증·증분 수집·캐시를 사용하고 상한에 도달한 실행은 완료가 아닌 부분 결과로 표시합니다.

R2

정적 분석의 오탐·미탐

지원 범위를 명시하고 도달성·PoC·중복 검토를 분리해 단일 신호가 제보로 직행하지 못하게 합니다.

R3

PoC 실행의 부작용

로컬 격리, 자원 제한, 네트워크·DB 스텁, scratch 쓰기와 허용 목록으로 실제 외부 효과를 차단합니다.

R4

자동화 결과의 과신

후보·재현·확정 상태를 구분하고 사람이 확인해야 할 질문과 미확인 범위를 보고서에 남깁니다.

DECISION REQUEST

제안하는 다음 결정
